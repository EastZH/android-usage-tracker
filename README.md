# Time — Android 手机使用记录

记录手机上每个 App 的前台使用时长，可回溯历史，并同步到电脑长期留存。

主要针对**杀后台极其激进的定制 ROM** 做了适配，
所以整个设计围绕"被杀了也不能丢数据"来做。

```
Android App ──导出──> 手机文件 ──adb──> 电脑 SQLite / CSV
```

## 它是怎么工作的

### 数据源：`UsageStatsManager`，不是常驻采集服务

App **不常驻后台**。Android 系统本身就在记录完整的使用情况，App 只是定期醒来把
系统已记好的数据取走。所以进程被杀掉完全不影响数据的完整性 —— 下次醒来补采即可。

权限 `PACKAGE_USAGE_STATS` 是 appop 型，不在运行时弹窗，两种授予方式：

```bash
# 一次性授予，重启后依然有效
adb shell appops set com.east.time GET_USAGE_STATS allow
```

或者：`设置 → 应用 → 特殊应用权限 → 使用情况访问`

### 整窗替换式幂等

每次同步把最近 24 小时的事件**整段删掉再全量写回**，而不是做增量去重。

因为事件时间戳只精确到秒，同一秒内完全可能出现 `RESUME→PAUSE→RESUME` 这样
同包名、同类型、同 class 的多条记录 —— 用唯一键去重会**误删合法数据**。
整窗替换从根上回避了这个坑，代价只是每次重写约 1 万行（每 15 分钟一次，可忽略）。

配合"原始事件只有 24 小时保留窗口"这个事实：**采集延迟几小时对最终结果毫无影响**，
只要一天内成功跑过一次就不丢数据。这是抵抗杀后台的关键。

### 数据保留

| | 保留 | 三年体量 |
|---|---|---|
| 原始事件 | **30 天**（超出自动裁剪） | — |
| 日聚合（自己推导） | **永久** | ~5.5 万行 / 几 MB |
| 日聚合（系统回填，仅 10 天） | 抄进自建表后永久 | — |

每天 1 万条原始事件三年就是 1100 万行（约 2GB），手机上撑不住，所以只留有界窗口；
真正长期保留的是每天每 App 的汇总。

**注意：只能往前攒，攒不回过去。** 系统的原始事件只有 24 小时、日聚合只有 10 天，
装上这个 App 之前的使用记录拿不回来。

### 统计从事件自行推导，不读系统日聚合

系统的"日"桶边界**不对齐零点**（实测某些 ROM 上是 00:56），拿它当"今天"会和直觉
差近一小时。所以日期一律按自然日切。（详见 `android-usagestats-bucket-quirks` 类注释）

## 构建

需要 JDK 17+ 和 Android SDK（`compileSdk 36`）。

```bash
./gradlew assembleDebug
```

没有 Gradle 也没关系，`gradlew` 会自己下载。

版本组合是**按互相兼容选的，不是按最新**：AGP 8.13.2 + Gradle 8.13 +
Kotlin 2.2.21 + KSP 2.2.21-2.0.5。改动前请先看 `build.gradle.kts` 顶部的说明 ——
KSP 从 2.3.0 起改了版本号规则，乱升会直接编译失败。

跑测试（纯 JVM，不需要设备）：

```bash
./gradlew testDebugUnitTest
```

## 安装与授权

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell appops set com.east.time GET_USAGE_STATS allow
```

> 部分定制 ROM 上 adb 安装需要额外开关（例如开发者选项里的 `Install via USB`），
> 不开会报 `INSTALL_FAILED_USER_RESTRICTED`。实在打不开就手动点 APK 安装。

## 同步到电脑

`pc/` 下有两个脚本，**手机上都不需要操作**。

### 方式一：电脑拉取（推荐）

```bash
python pc/sync.py
```

或双击 `pc\sync.bat`。数据落在 `pc/usage-pc.db`。

新鲜度取决于手机上最近一次同步（每 15 分钟一次）。

### 方式二：手机按一下

1. 双击 `pc\watch.bat` 挂着（关掉窗口即停止）
2. 手机 App 上点「导出」
3. 电脑自动拉取，手机显示「✓ 电脑已拉取」

手机上点一下会**先触发一次采集**，所以数据比方式一更新。

### 导出文件的两类语义

| 文件 | 可变？ | PC 端如何处理 |
|---|---|---|
| `rollup.csv` | 每次覆盖 | 整表替换 |
| `events-YYYY-MM-DD.csv` | **写完不变** | 只导一次（靠 `imported` 表判断） |
| `today-YYYY-MM-DD.csv` | 每次覆盖 | 整块替换（靠 `source_file` 删旧行） |

按天归档的文件必须等那天结束才写 —— 因为 PC 端靠"这个文件导过没有"决定是否导入，
文件一旦可变这个模型就崩了。但那样 PC 上永远看不到今天，所以单独给今天开一份可变文件。

⚠️ **跨天时会去重**：今天先以 `today-D.csv` 进过库，明天归档成 `events-D.csv` 时会先
删掉那份可变版本，否则同一天的数据会进两遍。

⚠️ **至少每 30 天同步一次** —— 手机只留 30 天原始事件，过期那段永久补不回来
（日聚合不受影响）。App 界面上显示「上次导出」就是为了让你一眼看出多久没搬过。

## 界面

- **两根管子**：上排 24 格选小时，下排 60 格（拆两行）是该小时的分钟。
  手指按在分钟格上会显示那一分钟是哪个 App。
- 选中某小时后，下方列表切换成该小时的各 App 时长；取消选择则显示当天总体。
- `[◀] [●] [▶]` 按当前口径翻页（今天 ±1 天 / 本周 ±1 周 / 本月 ±1 月），
  圆点回到当前周期。

## 已知限制

- **只读得到当前用户（user 0）**。应用分身 / 第二空间（user 999）的记录读不到，
  需要 `INTERACT_ACROSS_USERS`，普通应用拿不到。
- `NOTIFICATION_*` 事件、`instanceId`、`taskRootPackage` 都是 `@hide`，公开 API 没有。
- 同包两个同类 Activity 实例会被集合语义合并（`className` 去重），可能少算 ——
  已写成单测钉住。
- **亚秒级开合的 App 会少算**（实测某 ROM 的设置页 0.62 倍）：事件时间戳虽到毫秒，
  但同一秒内的碎区间累计仍有损耗。
- 系统回填的那些天**只有当天总量、没有分钟明细**，管子上会明确标注，
  不会画成空白（空白会被误读成"那天没碰手机"）。

## 项目结构

```
app/src/main/java/com/east/time/
  collect/UsageStatsSource.kt   读系统 API，权限检查
  analyze/SessionDeriver.kt     事件流 → 前台区间（纯函数）
  analyze/Bucketizer.kt         区间 → 可点选的格子（纯函数）
  data/                         Room：事件 / 自建日聚合 / 系统日聚合
  sync/SyncRepository.kt        采集、幂等写入、保留策略、导出
  export/ExportWriter.kt        导出给 PC 的文件
  ui/TimeGrid.kt                两根可点的管子（自绘 View）
pc/
  sync.py / sync.bat            电脑拉取
  watch.py / watch.bat          待命监听（手机按一下即同步）
```

`analyze/` 下两个是纯函数，有 21 个单测，改动它们请先保证测试通过。
